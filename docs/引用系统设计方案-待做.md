## 一、问题

### 1.1 现象（运行期实测，非推测）

一次完整的 flexible 流程跑通后，落到 `plans_flexible_sessions.steps` 的 Windows 路径出现了**多一层反斜杠**。逐层取证（`chat_messages.sequence_order`，均为"解析到底的最终字符串值"）：

| 层 | `C:\Users\woddp\Desktop\Downloads` 的实际值 | 判定 |
|---|---|---|
| `flexible_state` 存储层 | `C:\Users\woddp\Desktop\Downloads` | ✓ 单反斜杠 |
| 协调器传给 `flexible_step2` 的 `task_definition` | `C:\\Users\\woddp\\Desktop\\Downloads` | ❌ **双反斜杠** |
| 传给 `flexible_step4/step5` 的 `execution_trace` | 同上 | ❌ |
| 最终落库 | 同上（无损照抄） | ❌ |

**闭环证据**：`flexible_state` 里 step1 产出的 `task_definition` 是**单反斜杠**（干净），而协调器传给 step2 的同一字段是**双反斜杠** —— 中间**只有**一个环节：**协调器读 step1 的返回、写 step2 的参数**。

**老会话（`v1.0.0`）与新会话（`v1.0.1`）的中间链路都被污染** → 这是**系统性**的，不是偶发。

### 1.2 根因

> **数据在步骤之间传递时，由「协调器 LLM 从上一个 step 的 JSON 返回里读出值，再写进下一个 step 的参数」。**
> 遇到含 `\` 的值时，LLM 把「JSON 文本里已经转义过的 `\\`」误当成**值本身**，于是又转义一次 —— **每搬一次手，反斜杠就翻一倍。**

**为什么第一步不错、后面全错**：
- `user_message` 抄的是**用户原始消息**（纯文本，没有"已被 JSON 转义过"的外观）→ 只转义一次 ✓
- step 的**返回是 JSON 结构**，路径上已经压着一层转义 → LLM 再转一次 ❌

### 1.3 同类现象已经出现三次

| # | 现象 | 环节 | 状态 |
|---|---|---|---|
| 1 | `null` → `""`、`"array"` → `{"type":"array"}` | 协调器转抄模板给落库工具 | 已修（模板不经 LLM 手：改由回调存 `template_payload`，落库工具只收 `session_id`） |
| 2 | 数组 → `{"item": ...}` | step5 自己生成 JSON | 已修（prompt 补约束与示例，但仍不稳定） |
| 3 | `\` → `\\` | **step 之间的参数传递** | **本方案要解决的** |

**共性**：**凡是让 LLM 承担"结构化数据的搬运"，它就会在内容或转义上改坏。** 这不是某处代码写错，而是**架构层面的缺陷**。

### 1.4 为什么现有 `flexible_state` 解决不了

`flexible_state` 的定位是**状态机记录器**（记录 `current_step` 与"当前有效产物"），不是引用系统：

- `plans_flexible_service.rs:76` 的 `save_state` 走 **`update_content(&existing.id, …)`**（`:89`）→ **UPDATE，不新增行**
- `merge_state`（`:107`）是**读-改-写**：`products.insert(key, value)`（`:133`）→ **同 key 覆盖**

**即**：一个会话永远只有**一行**、**最新一份**产物。后果：

| 用户想做的事 | 现状 |
|---|---|
| 同会话重跑 step1（改了需求） | ✓ 覆盖（旧的不需要，够了） |
| `back_to_execute` 重跑 step2 | ✓ 覆盖 + 清下游（设计如此，对） |
| **「我要上一次那版 `task_definition`」** | ❌ 拿不到 |
| **对比 v1 / v2 两版产物** | ❌ 做不到 |

**所以引用系统必须独立设计**，不复用 `flexible_state` 的存储语义。

## 二、核心概念

| 概念 | 是什么 | 关键性质 |
|---|---|---|
| **Artifact** | 子 agent 产出的数据本体 | **不可变**，有新版本就产生新对象 |
| **Ref** | 指向 Artifact 的句柄 | **短字符串**（无转义风险），可带版本 / 字段路径 |
| **Run** | 一次子 agent **调用边界**的记录 | 追加式审计日志：**输入引用 + 最终输出 + 成败**；**不含内部多轮对话** |
| **Store** | Artifact / Run 的持久化 | trait 抽象，宿主注入实现 |

### Run 与 Artifact 的区别（最容易混，务必分清）

> **Run 回答「发生了什么」（含全部原始细节，不论成败）；Artifact 回答「产出了什么可以给别人用的东西」（干净、有身份、可引用）。**

类比：**Artifact = 仓库里的货物**（有编号、能被取用、能被运送）；**Run = 出入库台账 + 监控**（记录每次动作，供追溯，但不参与流转）。

同一次 `flexible_step2` 调用：

```
step2 子 agent 被调用一次
  ├─ Run 记录 1 条
  │    agent: "flexible_step2"
  │    input_refs: ["task_definition@3"]
  │    raw_output: "{\"status\":\"success\",\"execution_trace\":[…],\"compressed_context\":\"…\"}"
  │    status: "success"
  │    tool_calls: […]
  └─ Artifact 2 条（因为声明了这两个产物）
       execution_trace@1     ← payload = [{tool, input, …}, …]
       compressed_context@1  ← payload = "在 Downloads 目录下追加了一行时间戳"
```

| 这次执行里的东西 | 在 Run 里 | 在 Artifact 里 |
|---|---|---|
| 子 agent 的**整段原始输出** | ✓ `raw_output` | ✗ |
| `execution_trace`（声明过的产物） | 藏在 raw_output 里 | ✓ 独立成对象，可引用 |
| `compressed_context`（同上） | 藏在 raw_output 里 | ✓ 独立成对象 |
| `status: "success"` | ✓ `status` 字段 | ✗ **不做 Artifact**（状态信号，不是产物） |
| 内部调了哪些工具 / 耗时 | ✓ | ✗ |

**为什么必须分**：
- 只存原始输出 → 下游引用 `execution_trace` 要**每次现解析**，且没有版本、没有身份；或引用"整段 raw_output" → 又粗又脏
- 只存 Artifact → **失败时没有原始输出可复盘**（非定稿根本不产出 Artifact）

**粒度**：一次**子 agent 调用** = 一个 Run（不论内部跑了几轮 LLM、调了几个工具）。`run_id` 复用 `tool_call_id`，可与现有 `chat_messages` 对齐。

### ⚠️ Run 的覆盖边界（重要，别误读）

**Run ≠「子 agent 的会话上下文」。** 本方案**选 A：Run 只记「边界」** —— 输入引用 + 最终输出 + 成败状态，**不记内部多轮过程**。

**子 agent 运行期间的上下文，现状下根本没有持久化**（已核实，路径相对 `crates/planned-agent/src/`）：

| 事实 | 证据 |
|---|---|
| 子 agent 的 `ChatService` 用 `InMemoryStore`，写死在构造里 | `chat/service/service.rs:72` |
| `InMemoryStore::append` 是 no-op（直接返回空串，不存） | `chat/storage.rs:127-129` |
| 运行期的 LLM 请求/响应、自己的 tool_call、tool 结果只活在内存 | `chat/state/state.rs:158-162` |
| 挂起等用户确认时也只是内存里保住，仍不落盘 | `chat/sub_agent/session.rs:22-85` |
| `ChatService` 一 drop 全部消失（每次 `start()` 新建、完成即 drop） | `chat/sub_agent/runner.rs:97-107` |

**父 agent 每次只拿到「最后一条 assistant 文本」**：`extract_last_assistant_text`（`chat/sub_agent/collect.rs:188-198`）→ 包成 `ToolResult { content: Value::String(final_text) }`（`:154-158`）→ 作为**一条普通 tool 结果**写进**主 agent 的** `chat_messages`（同 `session_id`，`is_agent_tool=true`；`chat/handlers.rs:174`、`crates/agent-gui/src/storage/entity/chat_message.rs:22-24`）。

**这意味着**：Run 的 `raw_output` **就是那一条最终文本**，与主 agent `chat_messages` 里那条 tool 结果内容一致。**子 agent 中途调了哪些工具、试错几轮、为何放弃某个方案 —— 这些过程信息，本方案不留。**

**取舍理由**：换取「轻、零行为变化、能对账」；过程级复盘属另一个课题（见 §13 第 7 条）。

## 三、分层落位与通用性契约

| 层 | crate | 放什么 | 是否含业务 |
|---|---|---|---|
| **类型 + trait** | `crates/core`（新增模块 `artifact/`） | `ArtifactRef`、`ArtifactRecord`、`RunRecord`、`ArtifactStore` trait、`InputSpec` / `OutputSpec` | **零业务** |
| **运行时机制** | `crates/planned-agent`（`chat/sub_agent/`） | 装载器与 Run 记录器的**调用点** | **零业务** |
| **存储实现** | 新 crate 或 `agent-gui` | `SqliteArtifactStore`、`InMemoryArtifactStore` | 无业务 |
| **流程声明** | `agent-gui/src/pages/plan/flexible/` | flexible 的输入 / 输出声明表 | **业务在这里** |

**契约**：

1. `core` 与 `planned-agent` 中**不得出现** `flexible` / `step` / `plan` 等业务字样
2. **不配置装载器与记录器时，行为与现状逐字节一致**（两个钩子默认 `None`）
3. 接入一个新流程 = **只写它自己的声明表**，不改 `core` / `planned-agent`
4. 与既有 `hidden_args` 同级同性质（都是 `ChatConfig` 上的可选能力）

**参考的既有模式**：`crates/planned-agent/src/chat/storage.rs:88` 的 `ChatHistoryStore` trait —— "构造时绑定会话 + `InMemoryStore` 默认实现 + 宿主注入自定义实现"。本方案完全沿用该模式。

## 四、核心类型（Rust）

### 4.1 引用

```rust
/// 引用：指向「某会话 · 某产物 · 某版本 · 某字段」
#[derive(Clone, Debug, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct ArtifactRef {
    /// 作用域 —— 安全校验的依据（防跨会话越权）
    pub session: String,
    /// 语义类型，如 "task_definition"
    pub kind: String,
    /// None = latest
    pub version: Option<u32>,
    /// 可选 JSON Pointer（RFC 6901），字段级引用，如 "/params/目录"
    pub path: Option<String>,
}
```

**字符串形态**（可暴露给 LLM 传递，短且无转义风险）：

```
7feb4ba1-…/task_definition@3            → 指定版本
7feb4ba1-…/task_definition              → latest
7feb4ba1-…/task_definition@3#/params/目录 → 字段级
```

### 4.2 产物与执行记录

```rust
/// 产物：不可变
#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct ArtifactRecord {
    pub r#ref: ArtifactRef,        // 已解析出具体版本
    pub id: String,                // 主键（UUID）
    pub payload: Value,            // 数据本体
    pub producer_run: String,      // 由哪次运行产出
    pub schema: Option<Value>,     // 可选自描述
    pub summary: Option<String>,   // 可选人类可读摘要
    pub created_at: DateTime,
}

/// 执行记录：**调用边界的**审计日志，追加式
///
/// 注意：`raw_output` 是子 agent 的**最终文本**（= 交回父 agent 的那条 tool 结果），
/// **不含内部多轮对话过程** —— 子 agent 运行期上下文用 `InMemoryStore`，不落库。
/// 详见 §2「Run 的覆盖边界」。
#[derive(Clone, Debug, Serialize, Deserialize)]
pub struct RunRecord {
    pub run_id: String,               // 复用 tool_call_id
    pub session: String,
    pub agent: String,                // "flexible_step2"
    pub parent_run: Option<String>,   // back_to 重跑指向上一 run → 执行树
    pub input_refs: Vec<ArtifactRef>, // 它吃了哪些产物（声明式解析结果）
    pub resolved_hash: Option<String>,// 实际装载值的指纹（可观测性）
    pub raw_output: String,           // 最终输出文本（成败都记）—— 边界，非全过程
    pub status: Option<String>,
    pub is_error: bool,
    pub started_at: DateTime,
    pub finished_at: DateTime,
}
```

### 4.3 存储接口

```rust
#[async_trait]
pub trait ArtifactStore: Send + Sync {
    async fn put(&self, rec: ArtifactRecord) -> Result<ArtifactRef>;

    /// version = None 时解析为最新版本
    async fn get(&self, r: &ArtifactRef) -> Result<Option<ArtifactRecord>>;

    /// 会话产物清单（只回引用，不回 payload）
    async fn list(&self, session: &str) -> Result<Vec<ArtifactRef>>;

    async fn record_run(&self, run: RunRecord) -> Result<()>;
    async fn runs(&self, session: &str) -> Result<Vec<RunRecord>>;

    async fn gc(&self, policy: GcPolicy) -> Result<usize>;
}

/// 默认实现：不落盘（内存会话 / 测试 / 子 agent 临时会话）
pub struct InMemoryArtifactStore;
```

### 4.4 装载与记录钩子

```rust
/// 装载：按 InputSpec 从 ArtifactStore 取，并解析进参数
#[async_trait]
pub trait ArgLoader: Send + Sync {

/// 记录：子 agent 结束后写 Run + 按 OutputSpec 登记 Artifact
```

## 五、存储 Schema

沿用现有 migration 机制（sea-orm migration，表 `seaql_migrations`）新增两张表。以下是 SQLite 形态的参考 DDL：

```sql
-- 产物表：不可变，同 (session_id, kind, version) 唯一
CREATE TABLE artifacts (
    id              TEXT PRIMARY KEY,             -- UUID
    session_id      TEXT NOT NULL,                -- 作用域
    kind            TEXT NOT NULL,                -- 语义类型
    version         INTEGER NOT NULL,             -- 会话内同 kind 递增
    payload         TEXT NOT NULL,                -- JSON 文本；大对象时为空串
    payload_size    INTEGER NOT NULL,
    payload_path    TEXT,                         -- 大对象落盘路径（超过阈值时）
    schema_json     TEXT,
    summary         TEXT,
    producer_run_id TEXT NOT NULL,
    created_at      TEXT NOT NULL,
    UNIQUE (session_id, kind, version)
);
CREATE INDEX idx_artifacts_session_kind
    ON artifacts (session_id, kind, version DESC);

-- 执行记录表：追加式
CREATE TABLE agent_runs (
    run_id          TEXT PRIMARY KEY,             -- 复用 tool_call_id
    session_id      TEXT NOT NULL,
    agent           TEXT NOT NULL,
    parent_run_id   TEXT,
    input_refs      TEXT NOT NULL,                -- JSON 数组
    resolved_hash   TEXT,
    raw_output      TEXT NOT NULL,               -- 最终输出文本（边界，非全过程）
    status          TEXT,
    is_error        INTEGER NOT NULL DEFAULT 0,
    started_at      TEXT NOT NULL,
    finished_at     TEXT NOT NULL
);
CREATE INDEX idx_agent_runs_session
    ON agent_runs (session_id, started_at);
CREATE INDEX idx_agent_runs_parent
    ON agent_runs (parent_run_id);
```

**并发注意**：`version` 的递增（"取当前最大 + 1"）必须在**同一事务**内完成，否则并发重跑会同版本冲突。

**大对象**：`payload` 超过阈值（建议 64KB）时落盘，`payload_path` 记路径、`payload` 留空串；`ArtifactStore` 实现内部处理，调用方无感。

## 六、输入/输出声明

### 6.1 类型

```rust
/// 参数从哪来
pub enum InputSource {
    /// 默认：LLM 生成，原样保留（= 现状行为）
    Llm,

    /// 引用化：代码按 kind 从存储装载（version = latest）
    Artifact {
        kind: String,
        path: Option<String>,
        missing: MissingPolicy,
    },

    /// 钉死版本（回放 / 对比场景）
    Pinned(ArtifactRef),
}

/// 引用缺失时的策略
pub enum MissingPolicy {
    /// 缺 → 报错（Abort：不重试、如实上报）
    Error,
    /// 缺 → 给默认值
    Default(Value),
    /// 缺 → 给默认值，并在回执里标注「上游是 empty_result」
    AbsentAware(Value),
}

pub struct InputSpec {
    pub param: String,
    pub source: InputSource,
}

/// 输出的解析方式
pub enum OutputFormat {
    /// 输出是 JSON：`path = None` 表示整个 JSON 对象当一个产物
    Json { path: Option<String> },
    /// 输出是纯文本：整段原文 → `Value::String`，**不做 JSON 解析**
    Text,
}

/// 声明了产物、但按 `format` 取不到时的处理
pub enum OutputMissing {
    /// 静默跳过（不登记这条产物）
    Skip,
    /// 报错（Abort：不重试、如实上报）
    Error,
    /// 登记为 null（让下游明确看到"这里确实没有"）
    StoreNull,
}

/// 输出的哪部分成为产物
pub struct OutputSpec {
    pub kind: String,
    /// 怎么解析输出
    pub format: OutputFormat,
    /// false = 只进 Run 记录，不做可引用产物（如 `status` 这类状态信号）
    pub make_artifact: bool,
    /// 摘要字段路径（给主 agent 与用户看）
    pub summary_path: Option<String>,
    /// 取不到时的处理
    pub on_missing: OutputMissing,
}
```

**两种「文本」要分清**：

1. **整段是 JSON，只是其中某个字段是长文本**（如 `compressed_context`）→ **不是特例**：`path` 取出来自然就是 `Value::String`，照常处理。
2. **整段根本不是 JSON**（自由文本 / Markdown / 命令原始输出）→ **这才是特例**：用 `OutputFormat::Text`，整段原文直接成为一个字符串产物，不做 JSON 解析。

产物本体类型不受限（`payload: Value`，string / number / array / object 都行）。

**输出侧 `OutputMissing` 与输入侧 `MissingPolicy` 对称**：前者管「我该产出的东西没产出怎么办」，后者管「我要的东西没有怎么办」。

**`MissingPolicy::AbsentAware` 是通用解**：解决「上游确实没产出，但下游需要知道这件事」的场景（flexible 里的 `field_selection_result` 在 step3 走 `empty_result` 时不存在），而不是让下游拿到空对象去猜。

### 6.2 判定规则（何时传原值 / 何时传引用）

> **判据按「(step, 参数)」这一对，看它**这一刻**的来源。**

| 值的性质 | 传什么 | 理由 |
|---|---|---|
| LLM 这次**自己生成**（摘要、判断、自然语言指令） | **原值**（`InputSource::Llm`） | 它就是生产者，没有"转述"环节 |
| **短小标量**（枚举 / 布尔 / 数字 / 短词） | 原值（亦可走引用） | 无歧义字符，风险 ≈ 0 |
| **用户原始消息文本**（尚未进过存储） | **原值** | 纯文本、无 JSON 编码外观 → 抄不错（实测 ✓） |
| **前序产物 / 存储里的结构化值** | **引用** | ← 病根所在 |
| **大 payload** | **引用** | 保真 + 省 token |

**心法**：**「这次要新产生的」传原值；「已经存在、必须原样到达的」传引用。**
**补充**：值只要在存储里存在 → 一律引用；只在本次上下文首次出现的纯文本 → 原值。

### 6.3 不要按「大小」筛

| 你的疑问 | 答案 |
|---|---|
| 只输出 `ok` 也要写进引用系统吗？ | **Run 记录：要**（审计，一律记）；**Artifact：不要**（它是状态信号，不是产物） |
| 只有大文本 / 特殊字符串才写？ | **不是按大小，是按"下游用不用"**。大文本天然是产物，但它**不是"因为大"**才被记 |
| 统一走引用有副作用吗？ | 更简单、更省 token、子 agent 无感。唯一要求：该值**得有产物身份** |

**按大小筛的三个毛病**：① 大小不是本质（`ok` 也要能追溯）；② 同类东西走两条路 → 行为不一致、难测；③ 白添阈值与边界测试。

**反直觉但重要**：**引用比原值更便宜** —— 引用是十几个字符的短字符串，原值是一整段 JSON。

### 6.4 澄清：「引用」不是「值」的替代品

引用只是「**从存储到子 agent**」这段路上的**运输方式**；到了子 agent 手里**照样被解析成值**。

- 子 agent **看到的东西不变**（还是值）
- 变的只是**「谁把值装进去」**（代码 vs LLM）
- 子 agent 的 prompt **不用改**（它不需要知道"我收到的原来是引用"）

**schema 校验确认（已核实）**：`chat/tools/mod.rs:37` 中 `input_schema` 只被用于生成"给 LLM 的函数参数说明"，**全项目没有对 LLM 传参做 schema 校验的代码** → 代码注入的字段不会被拦。

### 主 agent 侧：回执（receipt）瘦身

引用化后，回调应把给主 agent 的返回值（`ResultDecision::Transform`）从"完整输出"改为回执：

```json
{
  "run_id": "r-17",
  "status": "task_defined",
  "artifacts": [
    {"kind": "task_definition", "ref": "7feb…/task_definition@3"},
    {"kind": "output_format",   "ref": "7feb…/output_format@1"}
  ],
  "summary": "已澄清为文件追写任务，输出为文本",
  "absent": ["field_selection_result"]
}
```

- `status` → 主 agent 决策用
- `ref` → 可转述、可传给下一步（**短字符串，无转义风险**）
- `summary` → 人与主 agent 看
- `absent` → 标明"上游确实没产出"
- **不含 payload**

**主 agent 想看内容** → 给它**只读**产物工具（阶段 5）；**要深入分析** → 下沉到下一个子 agent。

## 九、关键决策（必须早定）

| 决策 | 选择 | 理由 |
|---|---|---|
| 不可变性 | 新版本 = 新对象 | 回放 / 对比 / 回滚的前提 |
| `run_id` 来源 | **复用 `tool_call_id`** | 与现有 `chat_messages` 白捡对齐 |
| 引用格式 | `{session, kind, version?, path?}` | **预留版本位** —— 格式一旦落数据，改起来要动全部 |
| 版本解析 | `version: None` = latest | 流程内默认跟随最新；回放时用 run 记录里的具体版本 |
| 一致性 | **run 内钉死版本** | 防"混合版本"（装载中途上游重跑） |
| 安全 | **框架层强制校验 `ref.session`** | 防跨会话越权（IDOR）；不能靠业务层记得校验 |
| 缺省策略 | `Error` / `Default` / `AbsentAware` | 通用解掉 `empty_result` 型缺失 |
| 存储后端 | 小对象 DB / 大对象落盘（阈值） | 可扩展 |
| 钩子默认值 | `None` = 行为与现状一致 | 通用性 + 可回退 |
| **Run 覆盖范围** | **只记边界**：输入引用 + 最终输出 + 成败；**不存内部多轮 transcript** | 选 A：轻、零行为变化、够对账；子 agent 运行期上下文本来就不落库（§2） |
| 输出解析 | `OutputFormat::{Json{path}, Text}` | 兼容「整段不是 JSON 的纯文本输出」，不硬性假设输出一定是 JSON |
| 输出缺失 | `OutputMissing::{Skip, Error, StoreNull}` | 补上输出侧策略（此前只设计了输入侧 `MissingPolicy`） |

### 发布/订阅语义（回应「耦合太高」的质疑）

上游只声明 `produces`（**不知道谁消费**），下游只声明 `consumes`（**不知道谁产出**）—— 双方互不知情，这是 **pub/sub**，**不是"上游规划下游"**。

| | 现状（LLM 手传） | 引用化（pub/sub） |
|---|---|---|
| 上下游知道彼此吗 | **知道**（协调器 prompt 里写死"谁给谁"） | 互不知情 |
| 加一个新下游 | 改**协调器 prompt** | 新 step 自己声明 ✓ 不动别人 |
| 谁保证传对了 | LLM 的自觉（实测会错） | 代码（确定） |

**唯一共享的是「主题名」** —— 这是契约（如函数名、topic、HTTP path 一样），不是耦合缺陷。

**降低名字耦合的三个选项**：
- **A. 下游按需自取**（最松）：给只读工具，子 agent 自己取；代价是多一次往返，且必须守住铁律
- **B. 按契约/类型匹配而非名字**：更松，但更难读、更难查错（不推荐）
- **C. 声明集中到流程定义一处**（推荐）：耦合没少，但一眼看全，改时不会漏

**铁律**：**子 agent 如果要把上游的东西"给出去"，它给「引用」，不给「值」。**

## 十、与现有实现的关系 / 迁移路径

**并存，不替换**：

| 现有 | 引用化后 |
|---|---|
| `flexible_state.current_step` | **不变** —— 状态机档位仍由回调推进 |
| `flexible_state.products[kind] = <值>` | 长期退化为 `{kind: "ref"}` —— 从"存值"变成"存引用"，与 `artifacts` 表不再重复 |
| 各 step 的定稿登记回调（`step_callback/stepN/mod.rs`） | **继续用** —— 它决定"是否定稿 / 是否登记"，只是登记的落点从 `merge_state` 扩展到 `ArtifactStore` |
| `flexible_save_template` | **不变** —— 它已经是"引用式"（只收 `session_id`，从 state 读副本） |

**过渡期建议**：阶段 1、2 全部是**新增**（新表 + 新钩子），与现有存储**并行**，无迁移风险。到阶段 3 才改变参数传递路径；此时 `flexible_state.products` 是否立即退化为引用集合，可另议。

## 十三、未决问题

1. **`flexible_state.products` 何时退化为引用集合**？阶段 3 之后单独决策。
2. **GC 保留策略的具体参数**（最近 N 版、会话结束后归档多久）。
3. **只读产物工具是否暴露给主 agent**：暴露无害（它抄不了，因为参数槽已删），但会增加 token；是否默认开启待定。
4. **多流程共存时的命名空间**：`kind` 是否加流程前缀（如 `flexible.task_definition`）—— 若两个流程都要 `task_definition`，需要区分。
5. **`AbsentAware` 的下游语义**：下游子 agent 是否需要在 prompt 里被明确告知"这个字段是空因为上游没产出"。
6. **是否需要「对比视图」**（两个 run 的产物 diff）—— 属 UI 层，暂不在本方案范围。
7. **过程级复盘**（子 agent 内部多轮对话）：现状子 agent 用 `InMemoryStore`，**运行期上下文完全不落库**；Run 按选择 A 只记边界。若将来需要完整 trace，可选：① Run 增 `transcript` 字段；② 给子 agent 也用持久化 `ChatHistoryStore`（新增 `sub_agent_messages` 表，并给子 agent 一个会话身份）。**本方案明确不做**。

## 附录：术语表

| 术语 | 含义 |
|---|---|
| **Artifact（产物）** | 子 agent 产出的、可被下游引用的数据对象；不可变 |
| **Ref（引用）** | 指向产物的短字符串句柄，可带版本与字段路径 |
| **Run（执行记录）** | 一次子 agent **调用边界**的审计日志：输入引用 + 最终输出 + 成败；**不含内部多轮对话** |
| **Store（存储）** | Artifact 与 Run 的持久化抽象 |
| **声明（InputSpec / OutputSpec）** | 流程侧声明"我要什么 / 我产出什么" |
| **装载（Load）** | 代码按引用从存储取货、装进参数的过程 |
| **回执（Receipt）** | 给主 agent 的结果摘要：status + refs + summary，不含 payload |
