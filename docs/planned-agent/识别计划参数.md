# 识别计划参数 —— 让一次性脚本升级为可复用模板

> 版本：v1.0
> 创建：2026-08-06
> 状态：设计中（提前规划，尚未实现）
> 关联：`plan-storage-design.md` §4.2 todos JSON schema 的 `{{变量}}` 占位符

---

## 1. 问题

当前灵活模式执行完毕后，产出的是**针对特定输入的一次性计划**。

例如用户说"搜索安仁乡，点击资讯，获取最新的前三条信息，提取标题和介绍"，执行完毕后生成的计划只能复现"搜索安仁乡"这个具体任务。用户如果想搜索"天安门"，需要从头再执行一遍。

**核心需求**：让 AI 在执行完成后，自动识别"哪些值下次可能不同"，将其提取为**计划参数**，使计划从一次性脚本升级为可复用模板。

---

## 2. 概念：计划参数化

```
一次性计划:
  "搜索安仁乡" → 只能搜安仁乡

参数化计划:
  "搜索{{搜索关键词}}" → 传"天安门"就搜天安门，传"大竹县"就搜大竹县
```

**计划参数**（Plan Parameter）是嵌入在计划步骤中的占位变量。下次执行计划时，用户可以传入不同的值，计划行为随之改变。

### 与 `{{变量}}` 占位符的关系

设计文档 `plan-storage-design.md` §4.2 的 todos JSON schema 中已预留了 `{{变量}}` 机制：

```jsonc
{
  "step_id": "S2",
  "intent": "输入搜索关键词",
  "actions": [
    {
      "tool_name": "browser_type",
      "params": { "selector": "#kw", "text": "{{搜索关键词}}" }
      //                                         ↑ 计划参数
    }
  ]
}
```

识别计划参数就是**在对话层面引导用户确认**哪些值应该变成 `{{变量}}`。

---

## 3. 两个 Prompt 需要新增的行为

### 3.1 flexible_system.toml（灵活模式）

在"步骤 B：总结执行轨迹"之后、"步骤 C：引导固化"之前，新增：

**步骤 B2：识别计划参数**

回顾本次执行中的具体值（搜索关键词、文件名、URL、数值等），判断哪些值在下一次执行时可能不同。

分析原则：

| 应参数化 | 不参数化 |
|---------|---------|
| 来自用户输入的核心变量（搜索目标、文件名、查询条件） | 固定操作路径（"点击资讯标签"、"打开百度"） |
| 换一个值整个任务就变了的输入 | 结构性选择器（`#kw`、`.result-item`） |
| 用户可能重复执行但每次输入不同的内容 | 固定数量限制（除非用户明确说"前 N 条"中的 N 可变） |

识别后调用 `request_user_action` 引导用户确认。

**示例对话**（用户任务："搜索安仁乡，点击资讯，获取最新的前三条信息，提取标题和介绍"）：

```
AI 执行完毕 → 总结轨迹 → 识别参数 →

message:
  任务已完成。以下值可能是你下次执行时需要替换的变量，
  请确认哪些需要设为计划参数（可传参）：

actions:
  [
    { id: "param_search_keyword", type: "select", label: "搜索关键词 = 安仁乡 ✓",
      description: "设为参数后，下次可搜索其他内容" },
    { id: "no_param", type: "confirm", label: "都不需要，保持固定",
      description: "这个计划只用于搜索安仁乡" }
  ]

用户选择"搜索关键词 ✓"
  →
用户可选：自定义参数名，默认用 AI 推荐的名称
```

**引导原则**：
- AI 主动推荐候选参数，用户只需点击确认，降低认知负担
- 提供"都不需要"选项，不强制参数化
- 如果没有任何可变值（纯固定操作），跳过此步骤直接进入固化引导
- 参数名用中文，描述其含义（如 `{{搜索关键词}}`、`{{文件路径}}`、`{{目标URL}}`）

### 3.2 thorough_system.toml（周密模式）

在模式 A"信息完整 → 确认生成"中，融入参数化确认：

当前流程：
```
信息完整 → 总结需求 → 确认生成 ✓/还需补充 ✗
```

改进后流程：
```
信息完整 → 总结需求 → 识别可变值 → 参数化确认 → 确认生成 ✓/还需补充 ✗
```

**示例对话**（用户需求："搜索安仁乡，获取最新资讯"）：

```
AI:
  根据对话，我理解你的需求是：
  - 在百度搜索"安仁乡"
  - 点击资讯标签
  - 提取前三条资讯的标题和简介

  另外，搜索关键词"安仁乡"是否需要设为计划参数？
  参数化后，这个计划不仅能搜索安仁乡，还可以用于搜索其他关键词。

actions:
  [
    { id: "param_yes", type: "confirm", label: "设为参数",
      description: "搜索关键词作为可传参变量" },
    { id: "param_no", type: "confirm", label: "保持固定",
      description: "这个计划只用于搜索安仁乡" }
  ]

用户选择后 →
  → 确认生成（含参数化标记）
```

**规则**：
- 参数化确认在"确认生成"之前，作为一轮独立的交互
- 如果没有任何明显可变值（如"每天 9 点备份数据库"——没有可变输入），跳过此步骤
- 如果用户说"生成计划"时信息还不完整，先补全信息，再在确认阶段问参数化
- 遵循"单次交互只针对一个决策点"：参数化确认和最终确认生成分开两轮

## 4. 数据模型扩展

### 4.1 plans 表新增字段

```sql
ALTER TABLE plans ADD COLUMN params TEXT DEFAULT '[]';
-- JSON 数组，存储计划参数定义
```

### 4.2 参数定义 JSON schema

```jsonc
// plans.params
[
  {
    "name": "搜索关键词",           // 参数名（中文，用户可自定义）
    "key": "search_keyword",        // 变量键（用于 {{ }} 占位符引用）
    "default_value": "安仁乡",       // 默认值（本次执行使用的值）
    "description": "要在搜索引擎中查询的关键词",
    "affected_steps": ["S2"]        // 受此参数影响的步骤 ID 列表
  }
]
```

### 4.3 与 todos JSON 的关联

todos 中的 `{{变量}}` 通过 `key` 字段引用 params：

```jsonc
// plans.todos
[
  {
    "step_id": "S2",
    "intent": "输入搜索关键词并执行搜索",
    "step_type": "fixed",
    "actions": [
      {
        "tool_name": "browser_type",
        "params": { "selector": "#kw", "text": "{{search_keyword}}" }
        //                                         ↑ 引用 params[0].key
      }
    ]
  }
]
```

## 5. 用户体验流程

### 灵活模式 — 完整流程

```
用户: "搜索安仁乡，点击资讯，获取最新的前三条信息，提取标题和介绍"

AI 自由执行:
  ├─ browser_navigate("https://baidu.com")
  ├─ browser_type("#kw", "安仁乡")
  ├─ browser_click("#su")
  ├─ 等待结果 → 点击"资讯"标签
  ├─ 提取前三条标题 + 简介
  └─ 输出结果

AI 总结:
  ## 执行结果
  已获取安仁乡相关的最新三条资讯...

  ## 执行轨迹回顾
  1. 打开百度首页 → 成功
  2. 搜索"安仁乡" → 搜索结果已加载
  3. 切换到资讯标签 → 筛选出资讯内容
  4. 提取前三条 → 标题和简介已整理

AI 参数化引导:
  [request_user_action]
  message: "以下值可能是下次执行时需要替换的变量..."
  actions: [
    { id: "param_search_keyword", label: "搜索关键词 = 安仁乡 ✓" },
    { id: "param_count", label: "提取条数 = 3" },
    { id: "no_param", label: "都不需要，保持固定" }
  ]

用户点击 "搜索关键词 ✓" 和 "提取条数 ✓"
  ↓
AI: "参数已记录。搜索关键词将作为可传参变量，提取条数也支持自定义。"
  ↓
AI 固化引导:
  [request_user_action]
  message: "是否将本次执行轨迹固化为可传参计划？"
  actions: [
    { id: "generate", label: "确认生成" },
    { id: "edit", label: "还需补充" }
  ]
```

### 下次执行

```
用户打开计划 → 看到参数表单:
  ┌─────────────────────────────┐
  │ 搜索关键词: [安仁乡    ]    │  ← 默认值，可修改
  │ 提取条数:   [3         ]    │  ← 默认值，可修改
  │                             │
  │ [执行计划]                  │
  └─────────────────────────────┘

用户输入"天安门" → 点击执行
  → PlanAndExecuteAgent 将 params 注入步骤
  → S2: browser_type("#kw", "天安门")
```

## 7. 待决策项

| # | 决策点 | 选项 A | 选项 B |
|---|--------|--------|--------|
| 1 | 参数化引导的时机 | 执行完毕后自动触发（AI 主动识别） | 用户手动触发"设为可传参"按钮 |
| 2 | 参数默认值 | 使用本次执行的实际值 | 留空，强制用户每次输入 |
| 3 | 参数影响范围 | 记录 `affected_steps`，精确控制 | 全局替换，所有步骤中的同名占位符统一处理 |
| 4 | 参数名语言 | 中文（用户友好） | 英文 key（编程友好）+ 中文 label |

> **倾向**：1→A（AI 主动推荐），2→A（默认值降低使用门槛），3→A（精确控制避免误替换），4→A+B（中文 label + 英文 key 并存）
